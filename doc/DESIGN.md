## 1. 文档说明

- **本文定位**：MVP 的范围、判定逻辑、调度与告警设计、数据模型、实施计划与验收标准。
- **MVP 的三件事**（本次范围，其余全部后置）：
  1. **页面健康**——不以 HTTP 200 论正常，而是抓到内容后判断"这是不是一页正常的网站"；
  2. **内容变化**——若干个关键页面（主页 / 列表页 / 详情页等）与基线比对，变了就报；
  3. **定时巡检 + 邮件告警**——按"每天某时"或"每 N 小时"跑一次，有异常发邮件到指定邮箱。
- **明确不在 MVP**：服务器目录文件监测（需授权，已移出）、侵权检索、多用户、可视化报表、JS 渲染页抓取。

## 2. 需求逐项评估

### 2.1 MVP 需求清单

| 编号 | 需求 | 验收要点 |
| --- | --- | --- |
| R1 | 页面健康判定（内容优先） | 返回 200 的错误页 / 空白页 / 维护页必须判为异常 |
| R2 | 关键页面内容变化 | 多页面可比对；变了能说清"哪行变了" |
| R3 | 计划检测 | 每天固定时刻 或 每 N 小时；时区正确；错点补跑 |
| R4 | 邮件告警 | 一次巡检一封汇总；只报状态变化；恢复补发 |
| R5 | 自托管 | Docker + 飞牛 NAS，中文面板，装完即用 |
| R6 | 内容侵权发现 | 否决（见 2.2 R6） |
| R7 | 服务器文件完整性 | 移出 MVP（见 2.2 R7） |

### 2.2 逐项评估

#### R1 页面健康（核心，替代"200 即正常"）

| 维度 | 评估 |
| --- | --- |
| 科学性 | 成立，但属**启发式判定**。依据：真实站点故障时经常仍返回 200（nginx 默认错误页、CDN 拦截页、维护页、被挂马后的跳转页）。因此需要"传输层 + 响应层 + 内容层"三层证据综合判断，并由基线提供"正常长什么样"的参照。 |
| 落地性 | 中高。需要一张错误特征词库（中英双语）、长度/标题阈值、可选"必须包含文字"。不需要浏览器内核、不需要登录态。 |
| 预见性 | 可平滑升级：加"关键区块选择器""截图比对""视觉指纹"。判定引擎做成"规则列表 + 结论聚合"，后续加规则不改架构。 |
| 优点 | 直击真实痛点：200 的错误页、被跳转、空白页都能抓；判定**可解释**（告诉你是哪一条命中的），不是黑盒打分。 |
| 缺点 | 启发式必然有漏判与误判；JS 渲染站（SPA）抓不到正文，需明确告知而不是误报；反爬挑战页需专门识别并降级为"无法确认"。 |
| 结论 | **采纳**，并将"判定理由"作为一等公民输出（邮件和界面都要能看到依据）。 |

**判定分四档**（不是二元）

| 结论 | 含义 | 典型触发 | 是否邮件 |
| --- | --- | --- | --- |
| 正常 | 像一页正常网站 | 传输成功、内容规模与基线相当、未命中错误特征、关键断言通过 | 否（仅状态变化时发"已恢复"） |
| 可疑 | 有异常苗头，需人看一眼 | 正文比基线短 30%~60%、耗时 > 10s、跳到同域其他路径、标题变化但内容合理 | 是（标记"可疑"） |
| 异常 | 明确不可用 / 被改坏 | 命中错误页特征、正文近空白、关键断言缺失、跨域跳转、5xx、TLS 失败 | 是（加急） |
| 无法确认 | 被反爬或权限挡住，不能判断 | Cloudflare/JS 挑战页、403、需登录 | 是（只报一次，附"疑似反爬"说明） |

#### R2 关键页面内容变化

| 维度 | 评估 |
| --- | --- |
| 科学性 | 成立。规范化正文 + SHA-256 指纹 + 基线，是成熟做法。 |
| 落地性 | 中高。难点在**误报**：日期、访问量、随机推荐位、CSRF token 每次都在变。必须内置常见动态内容正则，并允许逐页自定义忽略规则。 |
| 预见性 | 可加"指定区块比对""忽略 HTML 区块"，数据模型（快照 + 基线）不变。 |
| 优点 | 与 R1 互补：R1 判断"是不是好的"，R2 判断"是不是原来的"。两者分开报，用户不会把"改版"误当"宕机"。 |
| 缺点 | 只比文字，图片/样式变化看不到；高频改动的列表页/详情页需要调规则；分页内容只覆盖第一页。 |
| 结论 | **采纳**。MVP 提供"忽略规则 + 基线确认 + 差异预览"三件套。 |

#### R3 计划检测（小时 / 天）

| 维度 | 评估 |
| --- | --- |
| 科学性 | 成立。低频巡检足以覆盖"被篡改/被打不开"，且对目标站点最友好。 |
| 落地性 | 高。容器内自带调度器即可，无需 cron 依赖；两种模式：`每天 HH:MM[,HH:MM...]` 与 `每 N 小时`。 |
| 预见性 | 可扩展为"站点级 + 页面级覆盖配置"、按工作日/周末不同节奏。 |
| 优点 | 实现简单、可预测、省资源；不会因高频轮询惹恼对方或被 CDN 限流。 |
| 缺点 | 发现延迟以小时计（用户可接受）；NAS 关机期间的巡检需要"补跑"逻辑。 |
| 结论 | **采纳**。默认**每天 09:00 与 21:00**（可改），抖动 ±90 秒，单站点每轮页面间间隔 3 秒。 |

#### R4 邮件告警

| 维度 | 评估 |
| --- | --- |
| 科学性 | 成立。SMTP 无平台绑定、可留痕。 |
| 落地性 | 高。国内邮箱走授权码；需处理 465/SSL 与 587/STARTTLS。 |
| 预见性 | 通知做成适配器，后续加 Bark/企业微信不动核心。 |
| 优点 | 一次巡检**一封汇总**，不会一天几十封；只报状态变化，不刷屏。 |
| 缺点 | 分钟级延迟；可能进垃圾箱；纯文本邮件在手机上看差异不够直观（用 HTML 版缓解）。 |
| 结论 | **采纳**（MVP 唯一渠道）。 |

#### R5 自托管（Docker + 飞牛 NAS）

| 维度 | 评估 |
| --- | --- |
| 科学性 | 成立。单容器 + SQLite + 网页 UI 是 NAS 场景最省事形态。 |
| 落地性 | 中高。零原生依赖规避 NAS 构建最常见的失败；镜像可离线导入。 |
| 预见性 | 可加反向代理 HTTPS、PWA、多用户。 |
| 优点 | 一条 compose 起来；备份就是拷 `data/` 目录。 |
| 缺点 | 依赖 Docker；NAS 休眠会中断巡检（用"补跑"兜底）。 |
| 结论 | **采纳**。 |

#### R6 内容侵权发现

| 维度 | 评估 |
| --- | --- |
| 科学性 | 不成立（作为全网发现）。无公开完整全网索引；搜索 API 有配额与覆盖限制。 |
| 落地性 | 低。投入产出比差，且容易让用户误以为系统能替其维权。 |
| 预见性 | 若未来接入，应为独立模块，不塞进内容监测。 |
| 结论 | **否决**（MVP 与后续都不做），替代方案：站内署名完整性（R2 的子集）+ 人工抽查 + 取证建议。 |

#### R7 服务器文件完整性

| 维度 | 评估 |
| --- | --- |
| 科学性 | 成立（路径 + 大小 + SHA-256 清单比对），但**前提是能读文件系统**。 |
| 落地性 | 取决于授权：本机可只读挂载；自有 VPS 需 SSH/挂载/探针；虚拟主机与他人站点**做不到，且不应探测路径**。 |
| 预见性 | 保留设计，将来拿到服务器权限可直接启用，数据模型不用改。 |
| 结论 | **移出 MVP**。界面标注"需授权"，不做任何目录探测。 |

### 2.3 需求间的依赖与冲突

| 关系 | 说明 | 处置 |
| --- | --- | --- |
| R1 与 R2 是两条告警线 | 混在一起会让"正常改版"看起来像"宕机" | 事件类型分开：`异常` / `可疑` / `内容变更` / `已恢复` |
| R2 与 R4 冲突 | 内容误报每天一封，用户会屏蔽邮件 | 内置动态内容正则 + 每页忽略规则 + 差异预览 + 同类 6 小时冷却 |
| R3 与 R1 冲突 | 巡检太频繁→对方限流/反爬，判定会误判为"异常" | 默认低频；识别反爬挑战后判"无法确认"，不升级为异常 |
| R3 与 NAS 休眠 | 关机期间错过巡检 | 启动时若超过计划间隔 1.5 倍，立刻补跑一次并标注"补跑" |

## 3. 技术选型（已裁决项 + 新增两项）

### 3.1 已定（2026-10-25 裁决）

运行时 **Node.js 22 LTS**、存储 **SQLite 单文件**、前端 **原生 HTML/CSS/JS**。

### 3.2 新增：抓取方式

| 选项 | 代价 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| **HTTP 抓取（内置 fetch）** | 无额外依赖，内存 ~0 | 快、省资源、可判断 200 错误页 | 抓不到 JS 渲染内容（SPA） | ✅ MVP 采用 |
| Headless Chromium（Playwright） | 镜像 +300MB，内存 +200~400MB，ARM 需额外构建 | 能测 SPA、可截图 | 在 NAS 上偏重，维护成本高 | 后续可选，不进 MVP |
| 第三方拨测 API | 需账号与费用 | 多地域视角 | 额外成本与依赖 | 不考虑 |

> MVP 对 SPA 的处理：**检测并如实告知**，不发假告警（见 4.6）。

### 3.3 新增：调度实现

| 选项 | 代价 | 优点 | 结论 |
| --- | --- | --- | --- |
| **应用内调度器**（每 20 秒检查一次"是否到点"） | 需处理时区/补跑 | 单容器自洽，无外部依赖 | ✅ 采用 |
| 容器 cron | 需额外进程与日志管理 | 简单直观 | 不采用 |
| 外部 cron + HTTP 触发 | 需暴露接口与密钥 | 灵活 | 不采用 |

## 4. 功能设计

### 4.1 页面健康判定（R1，核心）

**流程**

```
按计划触发 → 请求页面（20s 超时，跟随跳转，记录最终 URL）
   ↓
传输层：DNS / TCP / TLS 是否成功
   ↓ 失败 → 【异常】附原因（解析失败 / 证书错误 / 连接超时）
响应层：状态码、Content-Type、正文大小、最终主机
   ↓ 非 HTML / 跨域跳转 / 5xx → 【异常】
   ↓ 403 / 挑战页特征 → 【无法确认】（疑似反爬）
内容层：标题 + 正文规模 + 错误特征词 + 关键断言
   ↓
结论：正常 / 可疑 / 异常 / 无法确认（附命中理由）
```

**内容层判定表**

| 检查 | 规则（MVP 默认值） | 命中结论 |
| --- | --- | --- |
| 标题异常 | 空标题；或含 `404 / 500 / 502 / 503 / Error / Forbidden / 无法访问 / 该站点已暂停 / 建设中 / 维护` | 异常 |
| 错误页特征 | 正文前 2000 字命中内置词库（如 `Bad Gateway`、`该域名已过期`、`数据库连接失败`、`页面不存在`、`Service Unavailable`、`域名未绑定`、`站点已被暂停`） | 异常 |
| 正文近空白 | 去标签后正文 < 200 字 | 异常 |
| 正文骤降 | 正文长度为基线的 < 30% | 异常；30%~60% → 可疑 |
| 关键断言缺失 | 页面设置了"必须包含的文字"（如公司名、备案号、栏目名），未命中 | 异常 |
| 跳转到别的站点 | 最终主机与目标主机不同（`www` 归一化后比较） | 异常（劫持嫌疑） |
| 响应缓慢 | 耗时 > 10 秒 | 可疑 |
| 反爬挑战页 | 命中 `Just a moment`、`Checking your browser`、`验证您是否为真人`、`请开启 JavaScript` | 无法确认 |
| 需要登录 | 最终 URL 含 `login`/`signin`，或正文出现"请登录后查看" | 无法确认 |

**判定可解释**：每份结果保存 `reasons[]`（如"标题变为 502 Bad Gateway""正文 12,400 → 180 字"），邮件与界面直接展示，不出现只有分数的黑盒结论。

**与 R2 的关系**：健康判定先跑；内容指纹变化是**独立结论**。同一轮里既异常又变化时，只报"异常"，避免重复。

### 4.2 内容变化（R2）

- **归一化**：去 `<script>/<style>/<noscript>` 与注释 → 提取正文逐行 → 压缩空白 → 应用忽略规则（内置常见动态内容正则 + 页面自定义）。
- **指纹**：`sha256(归一化正文)`；与基线比对，不同即"内容变更"。
- **变更不等于故障**：单独事件类型，邮件标题用"内容变更"而非"异常"。
- **差异**：新增/删除行各前 15 条，带行号；界面可看全部。
- **基线**：首次成功检测自动成为基线；用户确认改版后点"设为新基线"。
- **忽略规则**：逐行正则；界面提供"预览比对文本"以校准（避免配错规则后静默失效）。

内置动态内容正则（默认启用，可关）：

| 目标 | 示例 |
| --- | --- |
| 日期时间 | `\d{4}[-/年]\d{1,2}[-/月]\d{1,2}`、`\d{1,2}:\d{2}(:\d{2})?` |
| 访问量/计数 | `访问量[:：]?\s*[\d,]+`、`阅读\s*[\d,]+` |
| 随机串 | `[0-9a-f]{16,}`、`[0-9a-f]{8}-[0-9a-f]{4}-…`（UUID） |
| 版本/构建号 | `v?\d+\.\d+\.\d+(-[0-9a-z.]+)?` |
| CSRF/时间戳参数 | `(csrf|token|ts|_t)=[^&\s]+` |

### 4.3 多页面组织（站点 / 页面两层）

```
站点（域名 + 检测计划）
 ├─ 主页        https://example.com/
 ├─ 列表页      https://example.com/news
 └─ 详情页      https://example.com/news/123
```

- **计划配在站点层**：所有页面同一轮巡检，避免每个页面各排一套时间。
- **页面层配置**：URL、必须包含的文字、忽略规则、敏感词、启用开关。
- 首版每站点建议 3~8 个页面；单站点上限 30 页（防误配）。
- 一轮巡检 = 一个批次（batch），用于汇总邮件与"本轮结果"展示。

### 4.4 检测计划（R3）

| 模式 | 配置 | 示例 |
| --- | --- | --- |
| 每天定时 | 一个或多个时刻 | `09:00` 或 `09:00, 21:00` |
| 每隔 N 小时 | N ∈ {1,2,3,4,6,8,12,24} | 每 6 小时（以启用时刻为起点） |

> **默认节奏已定（2026-10-25）**：每天 **09:00、21:00** 各一轮，时区 `Asia/Shanghai`，抖动 ±90 秒。

- **时区**：跟随容器 `TZ`（默认 `Asia/Shanghai`）。
- **抖动**：每个站点 ±90 秒随机偏移，避免整点同时打过去。
- **礼貌抓取**：同一站点内页面间隔 3 秒，串行；不同站点并发上限 2。
- **补跑**：服务启动时若"当前时间 - 上次巡检" > 计划间隔 × 1.5，立即补跑一轮，邮件标注"补跑"。
- **手动巡检**：界面上随时可点"立即巡检"，不影响计划节奏。
- **保护上限**：单站点每天最多 24 轮（配置错误时不至于把对方打爆）。

### 4.5 邮件告警（R4）

- **汇总**：一轮巡检结束时判断，有状态变化才发，**一封邮件覆盖本轮所有页面**。
- **只报变化**：正常→异常 / 正常→可疑 / 内容变更 / 异常→正常（恢复）。持续异常不重复轰炸。
- **冷却**：同一页面同一类型 6 小时内不重复（可配 1~24 小时）；恢复通知不受冷却限制。
- **主题示例**：`[网站哨兵] 🔴 2 个页面异常 · 1 个页面内容变更 · example.com`
- **正文结构**：异常（加急）→ 可疑 → 内容变更 → 已恢复；每项含 URL、判定理由、差异摘录（前 15 行）、处理建议、面板链接。
- **格式**：纯文本 + 简易 HTML 双版本，手机端可读；不使用外链图片。
- **测试**：设置页"发送测试邮件"，失败时给出具体 SMTP 错误（如 535 授权码错误、连接超时）。

### 4.6 能力边界（必须让用户看见）

| 情况 | 系统表现 |
| --- | --- |
| 页面靠 JS 渲染（SPA） | 抓到的正文 < 200 字且 HTML 含挂载容器（如 `<div id="app">`）→ 判定"无法确认"并提示"该页依赖 JS，本方案未启用浏览器渲染" |
| 有验证码 / Cloudflare 挑战 | 判"无法确认（疑似反爬）"，不计入异常，只报一次 |
| 需要登录才看得到的内容 | 判"无法确认"，提示需登录态（MVP 不支持登录态） |
| 页面本身是图片（海报页） | 正文近空白 → 会误判；建议该页关闭健康检查、只做可用性 |
| 目录/文件被改 | **不做**（需授权，见 R7） |

## 5. 架构与数据模型

```
浏览器 ──HTTP──> 容器内单进程
                 ├ 静态页面 + JSON API
                 ├ 登录鉴权（scrypt + HttpOnly 会话 + 登录限速）
                 ├ 调度器（每 20 秒判定"是否到点"，时区+抖动+补跑）
                 ├ 检测器（抓取 → 归一化 → 健康判定 → 指纹比对）
                 ├ 告警器（汇总本轮 → 邮件适配器 → 冷却控制）
                 └ SQLite（WAL，单文件 /data/app.db）
                                      │
                            出网 HTTPS → 目标站点
                            出网 SMTP  → 你的邮箱
```

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `sites` | id, name, base_url, schedule_mode(daily/interval), schedule_value, enabled, last_run_at | 站点与检测计划 |
| `pages` | id, site_id, name, url, must_contain(JSON), ignore_patterns(JSON), keywords, enabled, state, baseline_id, last_checked_at, last_message | 关键页面与当前状态 |
| `checks` | id, batch_id, page_id, ran_at, verdict(normal/suspect/bad/unknown), http_code, response_ms, final_url, title, text_len, reasons(JSON) | 每次检测结果（判定依据在此） |
| `snapshots` | id, page_id, kind(baseline/check), hash, text, meta | 正文快照；每页保留最近 60 份，基线永久 |
| `events` | id, batch_id, page_id, site_id, type(abnormal/suspect/changed/recovered/heartbeat/system), message, notified | 事件流，保留 180 天 |
| `settings` | key, value | SMTP、告警冷却、时区、密码哈希 |
| `sessions` | token_hash, expires_at | 登录会话，30 天 |

**状态机**

```
未检测 ─首轮─> 正常 ──异常──> 异常 ──恢复──> 正常（发恢复邮件）
                 │              │
                 ├─可疑──────> 可疑 ──恢复──> 正常
                 └─内容变更──> 已变更 ─设为基线─> 正常
```

## 9. 风险与限制

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 启发式误判（图片页、极简页） | 误报"异常" | 允许单页关闭健康检查；阈值可配；判定理由可追溯 |
| SPA / 反爬 | 判不出内容 | 明确判"无法确认"，不乱报；后续可选 Headless |
| 动态内容多（列表页、推荐位） | 每天一封"内容变更"变成噪音 | 内置动态正则 + 每页忽略规则 + 差异预览 + 冷却 |
| 低频导致发现延迟 | 最长等一个周期 | 用户可选每 N 小时；支持手动巡检 |
| NAS 关机/休眠 | 漏检 | 启动补跑 + 心跳事件（超过 2 个周期没跑 → 发"监测中断"提醒） |
| 邮件进垃圾箱 | 告警不到人 | 发信地址加白名单/SPF 建议；失败时界面明确报错 |
| 目标站点封 IP | 全部判"无法确认" | 频率克制 + 标识 UA + 失败不连环重试 |

## 10. 验收标准

1. 用一个**返回 200 但内容是 `502 Bad Gateway` 的页面**测试 → 必须判"异常"，邮件说明命中"标题/错误特征"。
2. 用**空白页（200，正文 30 字）**测试 → 判"异常"。
3. 正常页面 → 判"正常"，且连续多轮不发邮件。
4. 改主页一行文字 → 判"内容变更"，邮件给出增删行，不写成"异常"。
5. 添加 4 个页面（主页/列表/详情/关于）→ 一轮巡检**只收到一封**汇总邮件。
6. 配置"每天 09:00"→ 实际在北京时间 09:00±90 秒内执行；改系统时区到 UTC 后仍按配置时区执行。
7. NAS 停机一天后启动 → 立即补跑一轮，邮件标注"补跑"。
8. 站点挂掉 → 收到"异常"邮件；恢复后收到"已恢复"邮件。
9. 未登录访问接口被拒；连续错密码触发限速。
10. 常驻内存 < 100 MB，空闲 CPU ≈ 0。

## 13. 使用方法（目标形态）

1. 浏览器打开 `http://NAS内网IP:8686`，首次设置管理密码。
2. 设置 → 邮件通知：填 SMTP（QQ/163 用授权码）→ 发送测试邮件确认能收到。
3. 监测 → 新增站点：填地址与计划（默认每天 09:00、21:00）。
4. ＋页面：逐个添加主页/列表页/详情页；建议填"必须包含的文字"。
5. 点「立即巡检」建立基线，确认判定为正常。
6. 之后按计划自动巡检；收到邮件后点开面板看判定理由与差异，确认是正常改版就「设为基线」。

## 14. 容错设计

| 场景 | 行为 |
| --- | --- |
| 单页抓取失败 | 该页判异常，不影响同批其他页；网络错误重试 1 次，HTTP 5xx 不重试 |
| 整轮巡检被中断（进程重启） | 批次标记未完成，事件记 `system`；下次计划照常执行，不重复发已发邮件 |
| 邮件发送失败 | 重试 2 次（1/5 分钟）；仍失败则事件 `notified=0`，界面顶部提示 |
| SMTP 配置错误 | 保存时即可测试；错误码映射为中文提示（授权码/端口/证书） |
| 数据库异常 | WAL + `busy_timeout`；启动自检（`PRAGMA integrity_check`）失败则拒绝启动并提示恢复备份 |
| 升级迁移 | `PRAGMA user_version` 递增，迁移脚本幂等，失败回滚事务 |
| 时区/夏令时 | 调度统一用 `Intl.DateTimeFormat` 按配置时区计算，不依赖宿主机本地时区 |
| 磁盘满/无权限 | 写入失败记 `error` 日志并在界面横幅提示，不丢已有数据 |
| 目标站反爬 | 判"无法确认"并降频提示，不当成"被篡改" |

## 15. 代码审计要点

**安全**

- [ ] 所有 SQL 使用参数绑定，仓库内无字符串拼接 SQL
- [ ] 所有用户输入在输出时转义（前端 `escapeHtml`），后端不返回 HTML 片段
- [ ] 除 `/api/state`、`/api/login`、`/api/setup`、`/api/health` 外，所有接口校验会话
- [ ] 非 GET 请求校验 `Origin`；Cookie 为 `HttpOnly + SameSite=Strict`
- [ ] 密码用 `scrypt` + `timingSafeEqual`；会话表只存 token 的 sha256
- [ ] 登录失败限速（8 次 / 5 分钟 / IP）
- [ ] 静态资源按白名单返回，不接受用户拼接路径
- [ ] 日志与接口响应中不出现密码、Cookie、SMTP 凭据
- [ ] 依赖仅 `nodemailer`（MIT），升级前查阅安全公告

**逻辑**

- [ ] 判定优先级为 unknown > bad > suspect，且每条命中都写入 `reasons`
- [ ] 冷却只抑制"同类重复"，恢复通知不受抑制
- [ ] 同一站点不并发巡检；手动巡检与定时巡检互斥（409）
- [ ] `next_run_at` 计算覆盖跨日、多个时刻、补跑三种情况
- [ ] 差异输出有行数上限，不会因超大页面拖垮内存
- [ ] 忽略规则非法时在保存阶段报错，不在巡检时静默失效

**数据**

- [ ] 删除站点级联清理 pages/snapshots/checks/events
- [ ] 保留策略（快照 60 份、事件 180 天）在每日首轮后执行
- [ ] 基线永不被清理，换基线时旧基线降级为普通快照

**可运维性**

- [ ] 日志为 JSON Lines，含 `event/site/page/verdict/ms` 字段
- [ ] `/api/health` 不泄露内部状态（仅 `ok/version/db/lastRunAt`）
- [ ] 错误响应统一 `{ ok:false, error:{ code, message } }`，不含堆栈
