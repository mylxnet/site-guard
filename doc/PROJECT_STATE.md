## 3. 架构决策记录（ADR）

| 编号 | 决策 | 理由 | 备选与代价 |
| --- | --- | --- | --- |
| ADR-001 | 自建一体化，而非 Uptime Kuma + changedetection.io 组合 | 组合方案无法覆盖目录文件完整性，且两套面板/两套告警 | 组合方案成熟但运维成本高（详见 DESIGN 2.2） |
| ADR-002 | 单容器 + SQLite 单文件 | NAS 场景零运维；备份即拷目录 | PostgreSQL 需多一容器，属过度设计 |
| ADR-003 | 零原生依赖（`node:sqlite` + 内置 `fetch`） | NAS 上 `docker build` 最怕编译失败；ARM/x86 都能装 | 若不使用内置模块则需 better-sqlite3 等编译型依赖 |
| ADR-004 | 内容比对只比"正文文字"，不比整页 HTML | 随机 class、埋点脚本、内联样式会天天误报 | 整页比对更"严格"但会自我摧毁告警信誉 |
| ADR-005 | 目录一律只读挂载 | 监测程序不应有写权限，杜绝反向破坏 | 读写挂载可用于自动修复，但风险高 |
| ADR-006 | 邮件为首期唯一渠道，但做成适配器 | 零账号成本、可留痕；后续加 Bark/企微不动核心 | 多通道同时做会拖慢首版 |

## 4. 踩坑记录

### 坑 1：WSL 表面健康、实际无法启动

- **现象**：任何 `wsl.exe` 调用（含 `--version`、`-l -v`）都返回「系统找不到指定的文件」。
- **误导点**：`Microsoft-Windows-Subsystem-Linux` 与 `VirtualMachinePlatform` 均为 `Enabled`，Appx 包状态 `Ok`（2.7.12.0），`WslService` 正在运行 —— 所有常规检查都显示"已装好"。
- **根因**：`C:\Windows\System32\wsl.exe` 只是 217 KB 的旧版硬链接桩（指向 WinSxS），真正 4.29 MB 的程序在商店包里，启动即报 `Wsl/CallMsi/ERROR_FILE_NOT_FOUND`；`C:\Program Files\WSL` 有 `wslservice.exe`、`libwsl.dll` 却**独缺 `wsl.exe`**。注册表中产品 `{020F8AC8-A788-4E39-8E9B-8FECFA843632}` 的 `InstallSource` 指向已失效的 `e:\work\lxsyzd2004\lxsyzd\`，因此 `/fa` 修复必然触发 1706。
- **修复**：下载微软官方 2.7.12.0 MSI（签名校验 `Valid` / Microsoft Corporation）→ 按引擎期望原名 `wsl-2.7.12.msi` 放置 → 修复失败（1603/1706）→ 按产品码卸载（本机无 WSL 发行版，零数据风险）→ 全新静默安装 → `MainEngineThread is returning 0`。
- **教训**：
  1. WSL"功能已启用"≠"程序完整"，`--version` 都跑不通时直接看 `C:\Program Files\WSL` 缺不缺主程序。
  2. MSI 的注册源失效时，`/fa` 和重新 `/i` 都救不了，卸载重装才是最短路径。
  3. 提权进程可能读不到当前用户的 Temp 目录，安装包应放全机可读路径。

### 坑 2：阿里云 ACR 不支持 buildx 生成的 OCI 空层

- **现象**：`docker push` 到阿里云 ACR 时，各层都已 `Pushed`/`Mounted`，却在最后写 manifest 阶段报 `error from registry: unknown manifest class for application/vnd.oci.empty.v1+json`。
- **根因**：Docker 29.x 默认 BuildKit/buildx 会额外生成 OCI 格式 attestation/provenance 与 manifest list（含 `vnd.oci.empty.v1+json` 空层媒体类型），阿里云 ACR 不支持这类 OCI 扩展类型。
- **修复**：构建时加 `--provenance=false --sbom=false`（只关掉 attestation 来源，保留 BuildKit）；等价做法是经典构建器 `DOCKER_BUILDKIT=0 docker build`（整体回退 BuildKit）。
- **教训**：推给阿里云 ACR 的镜像须禁用 attestation/provenance，避免 OCI 扩展媒体类型。

### 坑 3：0.7.3 的 .fpk 装完打开还是“接口清单状态页”

- **现象**：`.fpk` 安装成功、网关入口也能打开，但界面始终是深色背景的接口清单页（`GET /api/health` 等），看不到设计里的四页签面板。
- **根因**：0.7.x 的正式前端 `public/` 只有一个占位状态页，四页签仍停留在 `prototype/`（假数据、不参与构建）；打包脚本只会复制 `public/`，所以装出来的包自然还是状态页。不是网关、也不是 fnOS 的问题。
- **修复**：0.8.0 把原型按真实 API 重写落进 `public/`（`index.html` / `style.css` / `app.js`），打包时随 `app/server/public/` 一起进包；`prototype/` 仅保留为设计参考。
- **教训**：验收要看**安装包里的实际前端产物**，不能拿 `prototype/` 当交付；`public/` 才是唯一交付面。

### 坑 4：0.8.0 实机装好、面板能打开但完全没有样式

- **现象**：页面结构出来了，但没有任何 CSS；顶部的登录卡片文案裸露在页面最上方，登录表单也不显示。
- **根因**：fnOS 桌面入口 `app/ui/config` 写的是 `"url": "/app/siteguard"`（**无尾斜杠**）。浏览器把该 URL 当页面名，页面里的相对路径 `style.css` / `app.js` 解析成 `/app/style.css`、`/app/app.js`；网关只转发 `/app/siteguard/*`，两个资源都 404。`app.js` 没加载，所以登录表单也没渲染。本地直连是 `/`，因此一直没暴露。
- **修复**：服务端返回 HTML 时按请求路径注入 `<base href="/app/siteguard/">`（直连注入 `/`）；CSP 的 `base-uri 'none'` 改为 `'self'`。这样 URL 带不带尾斜杠都能正确加载资源，且不用改 HTML/JS。
- **教训**：网关类应用的相对路径必须按**真实入口 URL**验证，不能只测带尾斜杠的地址；打包后的静态资源也要在模拟前缀下再跑一遍浏览器。

### 坑 5：0.8.1 实机输入两遍密码后提交，报「跨站请求被拒绝」

- **现象**：0.8.1 安装后页面与样式都正常，首次初始化输入两次密码点提交，返回 403「跨站请求被拒绝」；登录同样被拒。
- **根因**：飞牛统一网关把请求反向代理到 Unix Socket 时会改写 `Host`（浏览器发出的 `Origin` 是 NAS 地址，服务端看到的 `Host` 是转发后的地址）。`assertSameOrigin` 用 `Origin.host` 比 `Host`/`X-Forwarded-Host`，两者天然对不上，所有写操作都被判成跨站。
- **修复**：前端每个 API 请求带自定义头 `x-siteguard-client: 1`；服务端见到该头即视为同源页面请求并跳过比对。跨站表单无法伪造自定义头，跨站 `fetch` 加头会触发预检（本服务不返回 CORS 头，浏览器直接拦下），防御强度不降。不带该头的请求仍按原逻辑严格校验，`ALLOWED_ORIGINS` 白名单照常生效。
- **教训**：在网关/反代后面，`Origin` 与 `Host` 不可作为同源判定的唯一依据；要用浏览器能发、跨站发不出的信号（自定义头 / CSRF token）来区分。

### 坑 6：改了忽略规则仍报「内容变更」

- **现象**：给页面新增/修改忽略规则（如日期、访问量）后，下一轮巡检仍报「内容变更」；必须点一次「设为新基线」才能安静下来。
- **根因**：忽略规则只在抓取时过滤**当前文本**，基线里存的是**未过滤的旧正文**。比对时 `sha256(基线原文)` 与 `sha256(过滤后当前文)` 天然不同，`diffLines` 两侧也不对称，于是规则改动无法单独生效。
- **修复**：比对前用**当前忽略规则**把基线正文再过滤一遍（`baselineText`）；`contentChanged` 改比过滤后基线哈希，`diffLines(baselineText, extracted.text)`；喂给 R-08/R-14 的基线字数也改用过滤后字数，避免新增规则误判「正文骤降」/「正文下降」。旧基线原文不改写，删掉规则即可恢复。注意：规则若误过滤真实内容，会同时作用于当前文本与基线，差异中看不出来（可能掩盖变化）。
- **教训**：任何「过滤后的文本」与「历史快照」做比对，都必须对两侧按同一规则处理；只过滤一侧，规则改动就会表现成「必须重建基线」。

- 邮件冷却以“上一次真的发出去的变更邮件”为起点；SMTP 未配置或连续失败时不会推进冷却。

- 邮件只包含本批次事件；被冷却压制的事件保留 `notified=0`，不会在下一轮“补发”（避免过期告警）。
- 前端 `public/` 已接入真实 API；不支持的设置项（告警策略、巡检参数、改密码、导出备份）没有做成假控件，界面上不出现。
- 登录失败限速、批次进度都在进程内存，重启后清零/丢失；单实例自托管场景可接受。
- **目录监测依赖文件系统访问权**：只能监测已挂载的本机目录；远程网站无法读取目录，未授权站点不探测路径（已写入 DESIGN 4.3）。用户当前目标站点属于“他人站点或待定”，故首版以网页层监测为主，目录类型在界面标注“需授权”。

**发布流程（下次照做）**

1. 确认 `package.json` / `package-lock.json` / `fnos/siteguard/manifest` / 界面版本号 / 文档版本号五处一致。
2. WSL 内跑测试与打包，产出 `dist/fnos/siteguard-<版本>-x86.fpk` 与 `-arm.fpk`，按 `doc/FNOS_APP_DEV_GUIDE.md` §13.5 解包核对。
3. `git tag -a v<版本> -m "<说明>"`，`git push origin v<版本>`。
4. 建 GitHub Release（正文含「下载哪个 / 安装步骤 / 修复点 / 验证」），上传两个 `.fpk`；**附件名用 ASCII**，二进制不入 git。
5. 回填本表与 `CHANGELOG.md`。

> 环境事实：本机无 `gh` CLI，Release 通过 GitHub REST API 创建（`POST /repos/.../releases`，附件走 `uploads.github.com`）。token 不落盘、不写进仓库，用完即删。
